## Database Schema

The application uses a single PostgreSQL table in Supabase named `analyses`. Each row represents one completed Vastu analysis.

### Table: `analyses`

```sql
CREATE TABLE IF NOT EXISTS analyses (
    id                UUID         DEFAULT gen_random_uuid() PRIMARY KEY,
    created_at        TIMESTAMPTZ  DEFAULT now(),
    image_url         TEXT         NOT NULL,
    facing_direction  TEXT         NOT NULL,
    language          TEXT         DEFAULT 'en',
    parsed_floorplan  JSONB,
    user_corrections  JSONB,
    vastu_analysis    JSONB,
    overall_score     INTEGER,
    grade             TEXT,
    report_content    JSONB,
    report_language   TEXT         DEFAULT 'en',
    ip_hash           TEXT,
    user_agent        TEXT
);
```

### Column Descriptions

| Column              | Type          | Nullable | Default              | Description |
|---------------------|---------------|----------|----------------------|-------------|
| `id`                | UUID          | No       | `gen_random_uuid()`  | Primary key. Auto-generated UUID v4. |
| `created_at`        | TIMESTAMPTZ   | Yes      | `now()`              | Timestamp of when the analysis was created. |
| `image_url`         | TEXT          | No       | --                   | Public URL of the uploaded floor plan image in Supabase Storage. |
| `facing_direction`  | TEXT          | No       | --                   | User-specified compass facing of the property (e.g., "N", "NE", "E"). |
| `language`          | TEXT          | Yes      | `'en'`               | Language code for the analysis session. |
| `parsed_floorplan`  | JSONB         | Yes      | --                   | Structured output from Claude Sonnet 4.6 vision parsing. Contains rooms array, entrance data, plan shape, and confidence level. |
| `user_corrections`  | JSONB         | Yes      | --                   | Optional corrections submitted by the user during the review step (room name/type overrides). |
| `vastu_analysis`    | JSONB         | Yes      | --                   | Full scoring output from the Vastu rules engine: room scores, critical issues, positive aspects, and summary. |
| `overall_score`     | INTEGER       | Yes      | --                   | Weighted aggregate Vastu score (0-100). Extracted from `vastu_analysis` for indexing and querying. |
| `grade`             | TEXT          | Yes      | --                   | Letter grade derived from `overall_score`: A (85+), B (70-84), C (55-69), D (40-54), F (<40). |
| `report_content`    | JSONB         | Yes      | --                   | Natural language report generated by Claude Haiku 4.5. Contains summary, room details, priorities, positive notes, and tips. |
| `report_language`   | TEXT          | Yes      | `'en'`               | Language of the generated report. Updated when the user requests a report in a different language. |
| `ip_hash`           | TEXT          | Yes      | --                   | IP address from `x-forwarded-for` header. Used for rate limiting attribution. Stored as-is (not hashed in current implementation). |
| `user_agent`        | TEXT          | Yes      | --                   | Browser user agent string. Currently defined in schema but not populated by application code. |

### JSONB Column Schemas

**`parsed_floorplan`** conforms to the `ParsedFloorPlan` TypeScript interface:

```typescript
interface ParsedFloorPlan {
  rooms: Array<{
    name: string;                    // Human-readable room name
    type: string;                    // One of: kitchen, master_bedroom, bedroom, bathroom,
                                     //   living_room, dining_room, pooja_room, balcony,
                                     //   storage, corridor, study, utility, hall,
                                     //   drawing_room, unknown
    compass_direction: Direction;    // N, NE, E, SE, S, SW, W, NW, CENTER
    grid_row: number;                // Position in spatial grid
    grid_col: number;                // Position in spatial grid
    size: 'small' | 'medium' | 'large';
    has_window: boolean;
    has_door: boolean;
  }>;
  entrance: {
    compass_direction: Direction;
    grid_row: number;
    grid_col: number;
    side: string;                    // Which wall the entrance is on
  };
  total_rooms: number;
  plan_shape: string;                // e.g., "rectangular", "L-shaped"
  confidence: 'high' | 'medium' | 'low';
  error?: string;                    // Set to "not_a_floorplan" or "multiple_floors" on rejection
  message?: string;
}
```

**`vastu_analysis`** conforms to the `VastuAnalysis` TypeScript interface:

```typescript
interface VastuAnalysis {
  overall_score: number;             // 0-100
  grade: 'A' | 'B' | 'C' | 'D' | 'F';

    actual_direction: Direction;

    remedies: string[];
```

**`report_content`** conforms to the `ReportContent` TypeScript interface:


## Row Level Security Policies

RLS is enabled on the `analyses` table. The current V1 configuration uses permissive policies since there is no user authentication:

```sql
ALTER TABLE analyses ENABLE ROW LEVEL SECURITY;

CREATE POLICY "Allow all reads"   ON analyses FOR SELECT USING (true);
CREATE POLICY "Allow all inserts" ON analyses FOR INSERT WITH CHECK (true);
CREATE POLICY "Allow all updates" ON analyses FOR UPDATE USING (true);
```

| Policy Name        | Operation | Condition      | Notes |
|--------------------|-----------|----------------|-------|
| Allow all reads    | SELECT    | `true`         | Any client can read any analysis. Required for the shareable report page (`/report/[id]`). |
| Allow all inserts  | INSERT    | `true`         | Any client can insert new analyses. Server-side code uses the service role key, but anon key would also work given this policy. |
| Allow all updates  | UPDATE    | `true`         | Required for the regenerate-report endpoint, which updates `report_content` and `report_language` on existing rows. |

**Security note:** There is no DELETE policy. Rows cannot be deleted through the Supabase REST API. Administrative deletion must be done through the Supabase Dashboard or direct SQL access.

**Future consideration:** When user authentication is added, these policies should be scoped to the authenticated user's rows. The current open policies are acceptable for a free, anonymous tool but should not persist if user accounts are introduced.

## Indexes

```sql
CREATE INDEX IF NOT EXISTS idx_analyses_score   ON analyses (overall_score);
CREATE INDEX IF NOT EXISTS idx_analyses_created ON analyses (created_at);
```

| Index Name             | Column           | Purpose |
|------------------------|------------------|---------|
| `idx_analyses_score`   | `overall_score`  | Enables efficient filtering and sorting by Vastu score. Useful for analytics queries (e.g., score distribution, average scores). |
| `idx_analyses_created` | `created_at`     | Enables efficient time-range queries and chronological ordering. Supports rate-limit checks by IP and daily usage analytics. |

The primary key on `id` (UUID) provides an implicit unique B-tree index used for single-row lookups in the report page and regenerate-report endpoints.

## Supabase Storage

### Bucket: `floorplans`

The floor plan images are stored in a public Supabase Storage bucket.

| Property         | Value                  |
|------------------|------------------------|
| Bucket ID        | `floorplans`           |
| Bucket Name      | `floorplans`           |
| Public Access    | Yes (publicly readable) |
| File Size Limit  | 10,485,760 bytes (10 MB) |

### Configuration (from setup script)

```python
{
    "id": "floorplans",
    "name": "floorplans",
    "public": True,
    "file_size_limit": 10485760  # 10MB
}
```

### File Naming Convention

Files are stored with a timestamp prefix to avoid collisions:

```
{timestamp}-{original_filename}
```

Example: `1718234567890-my-floorplan.jpg`

### Storage Operations

The application exposes two storage functions in `src/lib/supabase/storage.ts`:

- **`uploadFloorPlan(buffer, fileName, contentType)`** -- Uploads a floor plan file to the `floorplans` bucket and returns the public URL.
- **`getFloorPlanUrl(fileName)`** -- Returns the public URL for a given file name without uploading.

### Graceful Degradation

The `/api/analyze` route handles storage upload failures gracefully. If the upload to Supabase Storage fails, the application continues with a truncated base64 data URL as fallback. This ensures the analysis pipeline is not blocked by storage issues.

## Supabase Client Configuration

Defined in `src/lib/supabase/client.ts`:

```typescript
import { createClient } from '@supabase/supabase-js';

const supabaseUrl = process.env.NEXT_PUBLIC_SUPABASE_URL!;
const supabaseKey = process.env.SUPABASE_SERVICE_ROLE_KEY
                 || process.env.NEXT_PUBLIC_SUPABASE_ANON_KEY!;

export const supabase = createClient(supabaseUrl, supabaseKey);
```

### Key Selection Logic

| Environment       | Key Used            | Reason |
|-------------------|---------------------|--------|
| Server-side (API routes) | `SUPABASE_SERVICE_ROLE_KEY` | The service role key is set as a server-only env var. It bypasses RLS and has full database access. Required for DB writes and storage operations from API routes. |
| Client-side (browser)    | `NEXT_PUBLIC_SUPABASE_ANON_KEY` | Falls back to the anon key when the service role key is unavailable (i.e., in the browser). The anon key respects RLS policies. |

**Important:** The service role key must never be prefixed with `NEXT_PUBLIC_` and must never be exposed to the browser. Next.js only bundles environment variables prefixed with `NEXT_PUBLIC_` into client-side code.

### Service Worker

File: `public/sw.js`

```javascript
// Minimal service worker for PWA install prompt
// VastuNow doesn't need offline support -- tool is useless without API

self.addEventListener('install', (event) => {
  self.skipWaiting();
});

self.addEventListener('activate', (event) => {
  event.waitUntil(clients.claim());
});

self.addEventListener('fetch', (event) => {
  // Pass through all requests -- no caching
  event.respondWith(fetch(event.request));
});
```

**Design rationale:** The service worker is intentionally minimal. It exists solely to satisfy the browser's PWA installability criteria (manifest + registered service worker). Since VastuNow requires live API calls for every analysis (Claude vision parsing, Vastu scoring, report generation), offline support would provide no value. All fetch requests are passed through to the network without caching.

```typescript
const nextConfig: NextConfig = {
```

### Configuration Details

| Setting                  | Value                              | Purpose |
|--------------------------|------------------------------------|---------|
| `images.remotePatterns`  | `https://*.supabase.co`            | Allows Next.js `<Image>` component to optimize and serve images from any Supabase project URL. Required for rendering uploaded floor plan images. |
| `serverExternalPackages` | `['@aws-sdk/client-bedrock-runtime']` | Excludes the AWS Bedrock SDK from the Next.js server bundle. The SDK is large and uses Node.js-specific APIs that can cause bundling issues. This ensures it is loaded natively at runtime. |

## Deployment Guide (Vercel)

### Prerequisites

1. A Vercel account (Pro plan recommended -- see timeout note below).
2. A Supabase project with the `analyses` table and `floorplans` storage bucket configured.
3. An AWS account with Bedrock model access enabled for `us.anthropic.claude-sonnet-4-6` and `us.anthropic.claude-haiku-4-5-20251001-v1:0` in the configured region.

### Step-by-Step Deployment

1. **Connect repository to Vercel:**
   - Import the Git repository in the Vercel Dashboard.
   - Framework preset: Next.js (auto-detected).

2. **Configure environment variables:**
   Add the following in Vercel Dashboard > Project Settings > Environment Variables:

   | Variable                          | Scope       |
   |-----------------------------------|-------------|
   | `AWS_ACCESS_KEY_ID`               | Production, Preview |
   | `AWS_SECRET_ACCESS_KEY`           | Production, Preview |
   | `AWS_REGION`                      | Production, Preview |
   | `NEXT_PUBLIC_SUPABASE_URL`        | Production, Preview |
   | `NEXT_PUBLIC_SUPABASE_ANON_KEY`   | Production, Preview |
   | `SUPABASE_SERVICE_ROLE_KEY`       | Production, Preview |

3. **Deploy:**
   - Push to main branch or trigger manual deployment.
   - Vercel will run `next build` automatically.

### Vercel Pro Plan Requirement

The `/api/analyze` and `/api/score` routes set `maxDuration = 60` (60 seconds). This is the maximum execution time for serverless functions on these routes.

- **Vercel Hobby plan:** Maximum function timeout is 10 seconds. This is insufficient for floor plan analysis, which involves Claude vision parsing and can take 15-45 seconds.
- **Vercel Pro plan:** Maximum function timeout is 300 seconds. The 60-second `maxDuration` setting works on Pro.

**If deploying on the Hobby plan,** the analyze and score endpoints will time out and return 504 errors for most requests. A Pro plan ($20/month) is required for production use.

### API Route Timeouts

| Route                       | `maxDuration` | Typical Latency | Operations |
|-----------------------------|---------------|-----------------|------------|
| `/api/analyze`              | 60s           | 10-30s          | Image upload to storage + Claude Sonnet 4.6 vision parsing |
| `/api/score`                | 60s           | 5-20s           | Vastu rules engine + Claude Haiku 4.5 report generation + DB insert |
| `/api/regenerate-report`    | 30s           | 3-10s           | Claude Haiku 4.5 report generation + DB update |
| `/api/report-pdf`           | Default (10s) | <1s             | DB read only (PDF is generated client-side) |

## Rate Limiting Strategy

### Current Implementation (V1)

The current V1 implementation stores the client IP address (`x-forwarded-for` header) in the `ip_hash` column of each analysis record:

```typescript
ip_hash: req.headers.get('x-forwarded-for') || 'unknown'
```

**Planned rate limit:** 5 analyses per IP address per day.

This can be enforced by querying the `analyses` table before creating a new analysis:

```sql
SELECT COUNT(*)
FROM analyses
WHERE ip_hash = $1
  AND created_at > NOW() - INTERVAL '24 hours';
```

The `idx_analyses_created` index supports efficient time-range filtering for this query.

### Limitations

- IP-based rate limiting is imprecise. Users behind shared NATs or VPNs will share a limit.
- The `x-forwarded-for` header can be spoofed in some configurations, though Vercel's proxy typically sets this reliably.
- There is no middleware-level rate limiting currently. The rate check would need to be added to the `/api/analyze` or `/api/score` route handlers.

### Recommended Enhancements

1. Add a Next.js middleware or route-level check that counts recent analyses by IP before proceeding.
2. Consider using Vercel's Edge Middleware with an in-memory store or KV for lower-latency rate limiting.
3. For stricter enforcement, implement fingerprinting or require an email/phone verification.

## Cost Breakdown

### Per-Analysis Cost Estimate

Each full analysis involves two LLM calls via AWS Bedrock:

| Step | Model | Input Tokens (est.) | Output Tokens (est.) | Cost per Call |
|------|-------|---------------------|----------------------|---------------|
| Floor plan parsing | Claude Sonnet 4.6 (vision) | ~2,000 (text) + image | ~800 | ~$0.012 |
| Report generation  | Claude Haiku 4.5            | ~1,500               | ~1,200 | ~$0.002 |

**Estimated cost per analysis: ~$0.014**

Additional infrastructure costs per analysis:
- Supabase Storage: Negligible (free tier includes 1 GB storage, 2 GB bandwidth/month).
- Supabase Database: Negligible (free tier includes 500 MB storage, 2 GB bandwidth/month).
- Vercel serverless: Included in plan.

| Daily Analyses | Monthly Analyses | LLM Cost/Month | Supabase (est.) | Vercel      | Total/Month |

## Data Retention Policy

### Current State (V1)

There is no automated data retention or cleanup policy in place. All analysis records and uploaded floor plan images are retained indefinitely.

### Storage Growth Projections

| Daily Analyses | Avg Image Size | Monthly DB Growth | Monthly Storage Growth |
|----------------|----------------|-------------------|------------------------|
| 100            | 500 KB         | ~150 MB (JSONB)   | ~1.5 GB               |
| 1,000          | 500 KB         | ~1.5 GB           | ~15 GB                |

### Recommended Retention Policy

1. **Floor plan images:** Delete from Supabase Storage after 30 days. The image URL stored in the database will become a dead link, but the analysis data (scores, report) remains useful without the image.

2. **Analysis records:** Retain indefinitely for analytics purposes, or archive to cold storage after 90 days.

3. **Implementation approach:**
   - Use a Supabase Edge Function or external cron job (e.g., Vercel Cron) to periodically delete old files.
   - SQL for identifying old records:
     ```sql
     SELECT id, image_url
     FROM analyses
     WHERE created_at < NOW() - INTERVAL '30 days';
     ```
   - After deleting the storage file, optionally null out the `image_url` column to indicate the image has been purged.

## Privacy Considerations

### Data Collected

| Data Point | Source | Storage | Sensitivity |
|------------|--------|---------|-------------|
| Floor plan image | User upload | Supabase Storage (public bucket) | High -- may reveal home layout, address if annotated |
| IP address | `x-forwarded-for` header | `ip_hash` column (stored as plaintext, not hashed despite column name) | Medium -- personally identifiable |
| Analysis results | LLM + rules engine | `vastu_analysis`, `report_content` columns | Low -- derived data |
| Language preference | User selection | `language`, `report_language` columns | Low |
| User agent | Browser | `user_agent` column (schema exists but not populated) | Low |

### Privacy Risks and Mitigations

1. **Public storage bucket:** Floor plan images are publicly accessible to anyone with the URL. The URLs use timestamp-prefixed filenames which provide obscurity but not security. Anyone who guesses or enumerates the timestamp prefix could access uploaded floor plans.

   **Mitigation:** Consider switching to a private bucket with signed URLs that expire after a fixed period (e.g., 1 hour). This requires generating signed URLs server-side when serving the report page.

2. **IP address storage:** The `ip_hash` column name implies hashing, but the current implementation stores the raw IP address. This is personally identifiable information under GDPR and similar regulations.

   **Mitigation:** Apply a one-way hash (e.g., SHA-256 with a salt) before storing the IP address. This preserves the ability to enforce rate limits while reducing PII exposure:
   ```typescript
   import { createHash } from 'crypto';
   const ipHash = createHash('sha256')
     .update(ip + process.env.IP_SALT)
     .digest('hex');
   ```

3. **No authentication:** All analyses are anonymous. There is no way for a user to view, export, or delete their own data. If a privacy regulation requires data subject access or deletion rights, there is no mechanism to identify which records belong to a given user.

   **Mitigation:** Implement a session token or optional email-based identification so users can manage their own analyses.

4. **Third-party data processing:** Floor plan images are sent to AWS Bedrock (Claude models) for analysis. This means the images transit through AWS infrastructure. AWS Bedrock does not use customer data for model training by default, but this should be disclosed in a privacy policy.

5. **No privacy policy page:** The application does not currently include a privacy policy or terms of service. For production deployment, especially if targeting users in the EU or India, a privacy policy disclosing data collection, storage, processing, and third-party sharing is recommended.

### GDPR / DPDP Compliance Checklist

- [ ] Hash IP addresses before storage
- [ ] Add a privacy policy page
- [ ] Disclose AWS Bedrock as a data processor
- [ ] Implement data deletion endpoint or admin tool
- [ ] Switch floor plan storage to private bucket with signed URLs
- [ ] Add cookie/consent banner if analytics are introduced
- [ ] Implement data export capability for user data access requests
